## The problem

amazee.io's documentation was spread across Confluence, GitLab, and Google Drive — with different teams using different tools in different ways. Developers were comfortable in GitLab but non-technical contributors weren't. Confluence was widely disliked. Google Docs had no structure or governance. The result was a knowledge base that nobody fully trusted: hard to navigate, hard to maintain, and impossible to search effectively.

Beyond the surface-level friction, there were deeper structural problems. Content ownership was unclear. Update notifications weren't happening. Version control was inconsistent. Onboarding and troubleshooting documentation was hard to find even when it existed. The system wasn't scaling — and it wasn't earning the trust of the people who needed to use it most.

## What I did

I led a full documentation transformation engagement — from the initial audit through to a completed platform migration. The work ran in three broad phases.

The first phase was research. I conducted in-depth interviews with eight workstream leads and contributors to map how documentation was actually being used, not how it was supposed to be used. From those interviews I built network diagrams, a conflict heatmap, and a requirements matrix covering 30+ criteria across eight workstreams. That matrix became the backbone for platform evaluation: which features mattered most to which teams, and where priorities diverged.

The second phase was evaluation. I researched 14+ documentation platforms, set up sandbox environments, attended vendor demos, and ran a structured usability trial with GitBook — building out a real GitLab integration, running task flows with both technical and non-technical users, and documenting what worked and what didn't. GitBook showed genuine promise for GitOps-style workflows, but the collaboration and permissions model didn't meet amazee.io's needs. Notion came out of the evaluation as the strongest fit. Throughout this phase I worked directly with the CISO to ensure that security and data sovereignty requirements were built into the evaluation criteria from the start — not bolted on at the end.

The third phase was migration. I designed and executed a 9-week end-to-end migration from Confluence and MkDocs to Notion. This included a full data backup in multiple formats (PDF, XML, CSV, HTML) before anything moved, the migration itself (I personally migrated and restructured all content into the new information architecture), stakeholder onboarding, live workshops and async training resources, and a post-launch support period. I also began a parallel cleanup of Jira and Monday.com to align operational tooling with the new documentation structure.

## How I approached it

The hardest part of this project wasn't the migration — it was getting alignment first. Documentation tools are surprisingly contentious: developers have strong opinions about GitOps workflows, security teams have requirements that can veto tool choices, and non-technical contributors just want something that doesn't feel like a barrier. Getting all of those perspectives into the same conversation, and finding a direction that everyone could live with, required the research phase to be rigorous and the outputs to be visual enough to make tradeoffs legible.

The requirements matrix and network diagrams weren't just deliverables — they were conversation tools. They made abstract disagreements concrete, which made it possible to resolve them. Cross-functional alignment at this level doesn't happen from a slide deck; it happens when people can see exactly where they agree and where they don't.

The GitBook trial is a good example of the discipline this kind of work requires. It would have been faster to skip the trial and go straight to a recommendation. But running the structured test — and documenting the real limitations — meant that when Notion was recommended, the decision was evidence-based and defensible. That matters for adoption.

## Key deliverables

- 30+ page findings and insights report covering tool comparisons, user needs, network diagrams, silo analysis, and alignment heatmaps
- Requirements matrix covering 30+ criteria across 8 workstreams with weighted priorities
- Structured GitBook usability trial with formal task flows, GitLab integration, and documented findings
- Migration roadmap and final platform recommendation (Notion, migrating from Confluence and MkDocs)
- Full content backup across PDF, XML, CSV, and HTML formats prior to any migration activity
- Hands-on migration of all content into Notion, restructured to the new information architecture
- Live workshops, enablement decks, and async training resources tailored for both technical and non-technical audiences
- Post-migration audit and consolidation of Jira and Monday.com operational systems

## Where it stands now

Migration is complete. amazee.io is running on Notion, with a documentation structure that both technical and non-technical contributors can navigate and maintain. The onboarding, troubleshooting, and workstream documentation that was previously scattered across three platforms is now searchable in one place.

The operational tool cleanup is ongoing — Jira and Monday.com are being consolidated to align with the new structure — but the core documentation work is delivered.

This project is different from most of what I build. There's no codebase, no deployment, no GitHub repo. The output is a living knowledge base and the organisational change that makes it useful. That's a different kind of hard — and it's one I found genuinely interesting.
