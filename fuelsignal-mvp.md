# FuelSignal MVP

> A procurement intelligence platform for independent UK fuel distributors — replacing gut-feel buying decisions with a daily BUY / HOLD / WAIT recommendation backed by four live signal layers and explained in plain English.

## The problem

Independent UK fuel distributors — typically businesses turning over between £5m and £100m — make procurement decisions (when to buy, how much, at what price) largely on instinct and experience. That's understandable: the signals that move fuel prices are scattered across multiple data sources that don't talk to each other.

Weather forecasts predict heating demand surges. Satellite crop data indicates when red diesel demand will spike at harvest time. Geopolitical news moves crude prices before markets fully reflect it. ICE Low Sulphur Gasoil spreads signal short-term price direction. Any one of these might change a buying decision. All four together, synthesised into a single recommendation, could meaningfully shift margins — especially for smaller distributors who can't afford a dedicated procurement analyst.

DGXC had deep domain knowledge of this problem and the data sources involved. What they needed was someone to turn that knowledge into a working product.

## What I built

FuelSignal ingests four signal layers every morning at 06:00 UTC — weather (Open-Meteo), satellite crop data (Leaf API), geopolitical signals (GDELT + NewsAPI), and live fuel pricing (OilPriceAPI). It scores each signal, weights and combines them, and produces a single **BUY / HOLD / WAIT** recommendation with a confidence level (HIGH / MEDIUM / LOW).

The "why" behind each recommendation is generated by Claude — 3 to 5 bullet points in plain English, the kind of thing a procurement analyst would say to a distributor: *"OPEC production cuts combined with a forecast cold snap across Yorkshire next week suggest a short-term demand surge. Recommend buying ahead."*

Every recommendation is stored with its underlying signal data, so accuracy can be tracked over time and the system can be tuned as real-world outcomes are observed.

The interface uses a financial terminal aesthetic — clean, dense, information-first — with Recharts for price history visualisation and Leaflet.js for regional UK GeoJSON maps showing where signals are strongest.

## How I built it

Solo build, but not from a blank page. The DGXC team provided extensive domain documentation — signal sources, weighting logic, how distributors think about procurement, what a "good recommendation" looks like in practice. That documentation formed the product specification, and I translated it into working software using my standard vibe coding approach with Claude and VS Code.

The interesting technical challenge here was the signal scoring and combination layer: how do you take four heterogeneous data sources (weather forecasts, satellite indices, news sentiment, price spreads) and produce a single, defensible recommendation? The answer involved normalising each signal to a 0–1 scale, applying domain-informed weights, and using confidence thresholds to determine when a recommendation is strong enough to be actionable.

The AI rationale component (Claude generating the plain-English explanation) came together quickly once the structured data model was in place. It's one of the more satisfying parts of the project — it makes the system's reasoning transparent rather than opaque.

## How long it took

Two days. That's the kind of timeline that raises eyebrows, but it's accurate. The domain documentation meant I didn't have to figure out the problem — I already understood it before I wrote a line of code. Clear problem, clear data sources, clear output format — the build itself was straightforward.

## Where it stands now

This is an MVP built to demonstrate the concept and support lead generation for DGXC — to show prospective clients what a tool like this could do for their procurement process. It's not yet connected to production data or deployed for live use.

The core logic is proven. Turning this into a production system would involve connecting to live APIs (rather than mocked/demo data), hardening the data pipeline, and building out the customer-facing onboarding flow. That's a different kind of project — and one that I'd be happy to scope if the lead generation succeeds.

This project is also a demonstration of a different kind of skill: taking someone else's domain knowledge and translating it accurately into software. That requires listening carefully, asking the right questions, and knowing when your documentation is complete enough to start building.
